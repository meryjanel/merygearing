# MeryGearing Project

> **좋아하는 게임에 있었으면 좋겠지만 없어서 만드는 기능**

## 서비스 링크

https://merygearing.xyz/ats/wiki

## Tech Stack

- Frontend: React, Next, @apollo-client, Dexie, Zustand,
- Styleing: Mui, Styled-Components
- Backend: Node, Express, Graphql, Typeorm
- Data & Crawling: Cheerio, Puppeteer, Sharp

## 주요 기능

- **다이얼로그 위키**: 모든 자원과 건물 정보 및 레시피 시각화
- **검색**: 초성 검색을 지원하는 빠른 데이터 필터링

## 핵심 기능: 재귀적 정보 탐색 (Card Stack UI)

게임 내 복잡한 자원 관계를 재귀적으로 탐색할 수 있도록 **다중 레이어 다이얼로그 시스템**을 구축.

- **연속적인 정보 탐색**: 상세 정보 내에서 조합법이나 재료 건물을 클릭하면, 현재 페이지를 벗어나지 않고 그 위에 새로운 다이얼로그가 쌓이는(Stack) 구조
- **맥락 유지 (Context Preservation)**: 이전 정보를 닫지 않고 위에 쌓아 올림으로써, 사용자가 복잡한 생산 체계를 추적하다가도 언제든지 이전 단계로 쉽게 돌아가는 경로 확보
- **Zustand 기반 상태 관리**: 열려 있는 다이얼로그들을 오직 키값만을 가진 전역 배열(Stack)로 관리하여, 순차적인 열기/닫기 동작과 데이터 일관성을 보장
- **통합 검색 연동**: 서비스 상단 헤더의 검색바를 통해 페이지 이동 없이 즉시 상세 정보를 다이얼로그로 호출 가능
- **범용 컴포넌트 설계**: 모든 연관 페이지에서 동일한 상세 정보 인터페이스를 공유하여 개발 생산성 및 유지보수성 향상

## Data Architecture & Performance

단순 데이터 출력을 넘어, 대규모 데이터 처리와 향후 확장성을 고려한 설계를 도입했습니다.

### 1. 차기 시뮬레이터 기능을 위한 IndexedDB 데이터 적재

- **Persistence**: 추후 구현될 '생산 시뮬레이터' 기능을 고려하여, 앱 실행 시 필요한 최소한의 메타데이터를 사용자의 브라우저(IndexedDB)에 적재
- **Efficiency**: 서버 요청을 최소화하고, 오프라인 환경에서도 핵심 정보에 즉시 접근할 수 있는 기반
- **Integrity** : IndexedDB는 테이블을 해쉬로 만들어서, 서버의 해쉬값과 비교하여 무결성을 유지하며, 적재되어있다면 서버에서 받아오지 않음.

### 2. 고속 탐색을 위한 검색 전용 경량 DB 구축

- **Search Optimization**: 전체 데이터에서 검색에 필요한 필드만 추출한 경량화된 검색용 DB를 별도로 운용
- **Fast Response**: 헤더 검색바에서 실시간으로 발생하는 쿼리에 대해 딜레이 없는 즉각적인 결과 피드백

## 기술적 성장 및 회고

### 1. IndexedDB를 활용한 클라이언트 사이드 데이터 설계

이번 프로젝트에서 처음으로 **IndexedDB**를 도입해 보았습니다.

- **도입 이유**: 향후 구현할 '생산 시뮬레이터'는 빈번한 데이터 계산이 필요합니다. 매번 서버와 통신하기보다 필요한 최소 데이터를 브라우저에 적재함으로써 **서버 부하를 줄이고 사용자에게 즉각적인 응답성**을 제공하고자 했습니다.
- **배운 점**: 브라우저 저장소의 생명주기와 비동기 데이터 처리에 대한 이해도가 높아졌으며, 프론트엔드 환경에서도 성능 최적화를 위한 '아키텍처 설계'의 중요성을 깨달았습니다.

### 2. 크롤링을 통한 데이터 자급자족과 정제

공식 API가 없는 환경에서 **Puppeteer**와 **Cheerio**를 활용해 수천 개의 아이템 데이터를 직접 수집했습니다.

- 단순히 데이터를 긁어오는 것에 그치지 않고, 가공 건물과 자원 간의 관계를 직접 정의하며 DB 구조를 설계하는 경험을 했습니다.
- **Sharp**를 이용한 이미지 최적화 과정을 통해, 대량의 에셋을 다루는 프로젝트에서 자원 관리 효율화의 필요성을 몸소 체험했습니다.

### 3. 복잡한 상태를 제어하는 Zustand와 Stack UI

여러 개의 다이얼로그가 겹치는 **Card Stack UI**를 구현하며 상태 관리 라이브러리의 중요성을 체감했습니다.

- Context API 대비 Zustand가 가진 성능적 이점(불필요한 리렌더링 방지)을 파악하고, 전역 상태를 배열(Stack)로 관리하며 복잡한 UI 로직을 깔끔하게 해결하는 법을 익혔습니다.
